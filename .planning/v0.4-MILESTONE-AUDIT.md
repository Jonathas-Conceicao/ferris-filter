checked off in the traceability table, and `roadmap.analyze` reports 100%. The author's

```
→ (no output)
```

`artifact_guard` and `generate_snapshot` pass with **zero** fixture re-baselining. The one

Two things stop this from being a pass.

## Gap 1 — Apply reports success after a failed save (BLOCKER)

The one code path whose ordering comment calls itself load-bearing is correct on the happy path
and silently inverted on the error path. `src/overlay/app.rs:493-497`:

```rust
if let Some(config) = &self.config {
    if let Err(message) = store::save(config, &self.store_path) {
        self.last_save_error = Some(message);   // recorded…
    }
}                                               // …and execution falls through
let outcome = match dynamic::compile_store(&paths, &self.store_path) { … };
```

There is no early return. When `store::save` fails — permission denied, disk full, the store
directory removed mid-session — Apply carries on and `compile_store` reads the **stale**
`dynamic.json` from disk. `write_filter` succeeds, so the `Written` branch (`app.rs:525-531`)
runs: it sets the success message, flips the indicator to *"filter matches saved rules"*, advances
`self.baseline` to edits that were never persisted, and clears `self.dirty`, which removes the
REVERT button.

The net effect is the worst available combination. The filter in the game folder does not contain
the edits; the stripe says it does; and the last-known-good baseline has been overwritten with
state that exists only in memory, so Revert can no longer recover it. The red `last_save_error`
line renders at `app.rs:384` at the same time as the green success line, so the UI contradicts
itself on screen.

Fix shape: treat a save failure as `ApplyOutcome::Failed` and return before compiling. The
contract documented five lines above — *"persist the store, THEN compile the filter from it"* —
already implies it.

**Affects:** DYN-03 (edits survive restarts), EDIT-09 (Apply writes the filter).

## Integration

**9 of 10 cross-phase connections wired**, 0 orphaned exports, 1 error-path break (Gap 1). Full
suite run in a scratch `CARGO_TARGET_DIR`: **364 unit + 36 integration + 1 doctest, 0 failures**.

Confirmed with call sites:

- The overlay drives Phase 12's lifecycle rather than reimplementing it. `dynamic::write_filter`
  has exactly **two** call sites crate-wide (`run.rs:177`, `app.rs:507`); `compile_store` likewise.
  Nothing else writes `dynamic.filter` bytes.
- Phase 12 drives Phase 11's compile API (`dynamic.rs:148-149`), and the overlay never touches
  `emitter::`/`pricer::` outside `#[cfg(test)]`.
- `RuleId` is session-only — no `Serialize`/`Deserialize` anywhere, dropped by `to_rules()`, and
  expansion state is keyed by it rather than by index. DYN-02 and PITFALLS §9 hold by construction.
- Phase 15 rides the existing `Rule`/`When` model: `Rule.name` (`config.rs:373`) reaches
  `emitter.rs:337`, `When.base_type` (`:341`) reaches the `BaseType ==` arm. No parallel schema.
- SYNC ECONOMY and Apply resolve the same directory (`store_path.parent()`), so the decoupled
  sync→Apply chain actually closes.

### Non-blocking integration warnings

**WARNING-1 — an unloadable store has no in-GUI recovery.** `dynamic::reset_store` has one call
site crate-wide (`run.rs:129`, i.e. `apply --reset`); nothing in `src/overlay/` calls it. This is
concrete rather than theoretical this milestone: `Styles.kite` is a non-`Option` field
(`config.rs:130`) under `deny_unknown_fields` (`:118`), so any `dynamic.json` seeded before the
`unidentified`→`kite` rename fails deserialization on **both** counts and is permanently
unopenable from `ff`. Recovery requires the CLI or deleting the file by hand.

**WARNING-2 — additive schema fields never reach an existing store.** `store::load` never
reconciles `dynamic.json` against `dynamic_base.json`. A store seeded before Phase 15 parses with
an empty `jewelleryClasses` (the field is `#[serde(default)]`) and silently omits the JEWELLERY
picker group. `edit.rs:848-851` has a test asserting exactly this, so the behaviour is known — but
the only remedy is `--reset`, which discards every rule. Every future additive field inherits it.

**WARNING-3 — the overlay drops `price_source`.** Already registered in STATE.md; the audit
records it because it is the single cross-phase value that reaches the overlay and is discarded,
and because it interacts directly with SYNC ECONOMY.

**WARNING-4 — the overlay resolves paths from the launch CWD** (`store.rs:81-84`), which is the
affordance CORE-02 existed to provide and the front end did not take up.

**WARNING-5 — no destination override in the overlay.** `install.rs:13-21` hardcodes the OneDrive
game folder. The CLI has `--dest` on both `apply` and `install`; the GUI has no equivalent, so
flow (c) is single-machine where flow (b) is not.

**WARNING-6 — two conventions for one contract.** `run.rs:138` compiles an `--store`-supplied
store against CWD-relative `prices.json`/`tiers.json`, while the overlay uses
`InputPaths::relative_to(store_dir)`. Harmless at defaults, inconsistent by construction.
