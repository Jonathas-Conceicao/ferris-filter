### Phase 999.3: Filter load info message — online filters only (BACKLOG, deferred)

**Status (2026-10-12):** deferred. The in-game load message **is only possible for online
filters**, i.e. filters stored on the player's pathofexile.com account. FerrisFilter's local
`.filter` output cannot show it (see the spike results below). This item stays parked until we decide to
publish filters to the account, which is a later, outward-facing feature (see "Next spikes"). The
economy-overview half of the original idea moved to the overlay (999.4) and no longer depends on
this item.

**Goal:** Show an info message when the filter is loaded in-game, the way FilterBlade does
(observed 2026-10-11: `Name: filterblade` / `Version: 0.10.4.2026.283.13` / `Last update: 11 October
2026 at 04:29 PM`), by publishing FerrisFilter output as an online filter. Message content should
come from configuration (see 999.8).

**Research (2026-10-11).** The same FilterBlade filter was installed in two ways:
`OnlineFilters/pgWoKpuQ` (a GGG online-filter subscription, which *shows* the message) and
`filterblade.filter` (downloaded into the game folder by hand, which *does not*). Apart from
trivial comment noise the filter bodies are the same. The message is not a filter directive. It
comes from a 10-line metadata header that the game's online-filter sync puts at the top of the
file:

```
#Online Item Filter
#name:filterblade
#version:0.5.5e
#realm:poe2
#errors:
#hash:f6b696a2a8858865309b37cddab4e40a
#filterVersion:0.10.4.2026.283.13
#filterType:Normal
#lastUpdate:2026-10-11T17:15:26Z
#monthTimeStamp:1522
```

The header lines end in LF and the body uses CRLF. `#hash` is the **MD5 of the body bytes as-is**
(everything after line 10, CRLF kept); this was verified to match. The online files have no `.filter`
extension and are named by the online filter's id.

**Spike results (2026-10-12, author-tested in-game).** The test filters were the current
`dynamic.filter` with a FerrisFilter version of the online header and a correct body hash.

- **The offline header is ignored.** `ff-header-test.filter`, `ff-badhash-test.filter` (wrong hash)
  and `ff-freetext-test.filter` (free text in `#name`/`#filterVersion`/`#errors`) all appeared in
  the dropdown and loaded with only the stock "Item Filter loaded successfully." message. An offline
  file cannot produce the load message, whatever its header says.

- **`OnlineFilters/` is a cache, not a source.** Two hand-written files placed there (`ffTEST01`,
  `ffTEST02`) never appeared in the dropdown, and the game left them untouched. The online list
  comes from the account's filters on the server; the folder only holds downloaded copies.

- **Local edits to a subscribed online filter are overwritten.** The header of the real FilterBlade
  copy (`OnlineFilters/pgWoKpuQ`) was rewritten with marker values (`#name`, `#filterVersion`,
  `#errors`, `#filterType`, a 2030 `#lastUpdate`), with the body and its hash left intact. When the
  filter was loaded, the game replaced the file with the server's version, byte-for-byte. So the
  game checks against the server, not against `#hash`, and the local file is not something we can
  patch.

**Consequence:** the load message is only available to filters that really are **online**, meaning
filters stored on the player's pathofexile.com account. Getting it means publishing the
FerrisFilter output to the account instead of (or as well as) writing a local file.

**Next spikes (unverified):**

1. Cheap manual check: create an online filter on pathofexile.com by hand, paste a FerrisFilter
   output into it, subscribe in-game, and confirm the message shows. Also note which displayed
   fields map to which values entered on the site (name/version/last update), whether any can carry
   free text (that would let a future version echo 999.4's economy summary in-game), and whether the
   `CustomAlertSound "uwu.mp3"` still works from an online filter.

2. Automated path: GGG's developer API appears to expose item-filter create/update endpoints under
   an OAuth scope (FilterBlade's auto-updater is believed to use this). Confirm the endpoints, the
   scope, and what app registration GGG requires. This would replace `install`/`apply`'s local copy
   with an account upload, which is outward-facing and needs explicit opt-in. Also check
   whether there are rate limits, or limits on how many filters an account can hold.

### Phase 999.18: NVIDIA overlay treats `ff` as a game (BACKLOG)

**Goal:** Stop the NVIDIA app's overlay / recorder from treating the `ff` window as a game
(browsers and terminals are left alone; `ff` gets the "Alt+Z" overlay popup like a game). `ff` is
left as is until then. Raised by the author on 2026-10-18.

**Findings (2026-10-18, author's machine):**
- `ff` renders through wgpu (eframe 0.36), which picks a backend at start-up; egui-wgpu honours
  `WGPU_BACKEND`. Tested: `dx12` and `vulkan` trigger the NVIDIA overlay, `opengl` does not. The
  author prefers not to switch the rendering library or backend just for this.
- NVIDIA's Vulkan driver manifest (`nv-vk64.json`) declares implicit layers `VK_LAYER_NV_optimus`
  (`DISABLE_LAYER_NV_OPTIMUS_1`) and `VK_LAYER_NV_present` (`DISABLE_LAYER_NV_PRESENT_1`).
  `WGPU_BACKEND=vulkan` + `DISABLE_LAYER_NV_PRESENT_1=1` did **not** stop the overlay.
- No official NVIDIA "not a game" flag was found. Known route: a per-application driver profile
  with setting `0x809D5F60` = `0x10000000` (applied by hand with NVIDIA Profile Inspector; reported
  to stop working on some drivers). Apps can write the same profile through NVAPI DRS
  (`NvAPI_DRS_*`), reported to need administrator rights, which the per-user installer does not
  have. Not tested yet: in Profile Inspector, create a profile for `ff.exe`, set `0x809D5F60` to
  `0x10000000`, launch `ff`.
- Other apps fixed the same symptom by switching to OpenGL (SignalRGB).

**Options to evaluate:** test the driver-profile setting; if it works, an optional elevated "fix
NVIDIA overlay" action or a README note; otherwise an OpenGL renderer (eframe `glow`, or wgpu's GL
backend pinned), possibly behind a setting; ask NVIDIA to add `ff.exe` to their application
database.

- https://www.nvidia.com/en-us/geforce/forums/discover/262665/how-to-fix-share-shadowplay-overlay-showing-up-in-non-game-application/
- https://forums.developer.nvidia.com/t/gfe-and-g-sync-is-activated-by-a-regular-application/266188

### Phase 999.20: Throttle server requests to once per hour (BACKLOG)

**Goal:** Each kind of server request the overlay makes is sent at most once per hour, however
often the user clicks. A click inside the hour does not reach the server: it "fake-refreshes",
running the normal flow and outcome from the last result, so it looks the same as a real refresh.
Applies to the overlay's three network actions: **Sync economy** (poe.ninja exchange + unique
overviews; the hour is per league, so picking another league still syncs), the **League** list
refresh (poe.ninja `index-state`) and **Check for updates** (GitHub `releases/latest`). A failed
request does not start the hour, so a retry after an error goes out. Open points: whether the
last-request times survive a restart (e.g. in `ff-settings.json`, or the `prices.json` timestamp
for Sync), and whether the CLI (`ff-cli sync`, `sync metadata`) is throttled too or left as an

### Phase 999.21: Crash log for the overlay (BACKLOG)

**Goal:** When `ff` dies, leave a file that says why. Raised by the author on 2026-10-20 after a
release `ff` vanished between two hotkey presses (relaunching worked and it ran fine afterwards);
nothing was left to investigate. Always on, no flag needed.

**Findings (2026-10-20):** Windows recorded no Application Error / WER event (IDs 1000-1002) for
`ff.exe` in the previous 14 days. That fits a Rust panic: a panic unwinds and exits quietly (no
WER report), and the release build is a GUI-subsystem exe, so the panic message on stderr goes
nowhere. A native fault (access violation, stack overflow, abort) would normally show in WER.

**Scope:**
- **Where:** `%LOCALAPPDATA%\FerrisFilter\logs\` (local, not the roaming `%APPDATA%` folder; not
  `%TEMP%`, which Disk Cleanup and Storage Sense empty). Keep the last few crash files.
- **Panics (main and worker threads):** a `std::panic::set_hook` writing timestamp, version (the
  About tab's `build_info` string), OS version, thread name, panic message and source location,
  and a backtrace. A worker-thread panic today only ends that thread; log it too.
- **Native crashes:** an unhandled-exception filter writing a minidump (`MiniDumpWriteDump`, or a
  crate such as `minidumper` / `crash-handler`). WER `LocalDumps` is not an option: its key is
  under HKLM and the per-user installer has no admin rights.
- **Symbols:** release builds use `strip = true`, so backtraces have no names. Either keep line
  tables and publish the `.pdb` as a release asset (not in the installer), or at least record
  module base and offsets so a dump can be symbolized later.
- **Silent exits:** a "running" marker file written at start and removed on a clean Quit; if it is
  still there at the next launch, the previous session ended unexpectedly (killed, crash the hooks
  missed). Then say so once on the status line, with the logs folder.
- **Context:** the crash file includes the last ~200 lines of the in-memory log buffer from 999.22,
  even when file logging is off.
- **Entry point:** an "Open logs folder" link (About tab) so a user can send the file.
