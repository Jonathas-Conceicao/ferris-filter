  </read_first>
  <action>
    Configure the viewport so the window satisfies SHELL-01 and SHELL-03 and dodges five of the six
    documented egui overlay defects by construction.

    Create `src/overlay/layout.rs` with a **pure** function
    `pub fn dock_rect(monitor: egui::Vec2, width: f32) -> egui::Rect` plus
    `pub const STRIPE_WIDTH: f32` (460.0, per D-23's measurement) and
    `pub const EDGE_MARGIN: f32`. `dock_rect` returns the stripe's outer rect docked against the
    right screen edge with `EDGE_MARGIN` clearance on the right, top and bottom, and it must
    guarantee — as an invariant, not a coincidence — that the returned width is strictly less than
    `monitor.x` and the returned height is strictly less than `monitor.y` (D-12, egui #4458). Clamp
    rather than trusting the inputs, so a small monitor or a silly width still yields a sub-screen
    rect. Unit-test it: a 1920×1080 monitor yields a 460-wide rect flush to the right edge minus the
    margin; height is strictly under 1080; a 400×300 monitor still yields a rect strictly inside it;
    a requested width larger than the monitor is clamped.

    In `overlay::launch`, build `eframe::NativeOptions` with a `viewport: egui::ViewportBuilder` that
    sets: `with_always_on_top()` (D-13), `with_decorations(false)` (D-14 — all chrome is ours, the
    header plate is drawn in plan 13-04), `with_inner_size([STRIPE_WIDTH, 1000.0])` as the
    pre-monitor-query default, `with_resizable(false)`, `with_taskbar(false)` (D-16 — the tray is the
    presence indicator, not the taskbar), and `with_active(false)` so the very first reveal does not
    steal focus. Explicitly do **not** call `with_transparent(true)` (egui #4451/#4446), do **not**
    call `with_mouse_passthrough(true)` (egui #2537), and do **not** call `with_fullscreen(true)`
    (egui #4091) — the window is opaque and non-passthrough by omission, which is the whole point of
    D-13. Set `viewport.with_title("FerrisFilter")` for the OS-level identity even though no
    decoration shows it.

    In `OverlayApp::update`, on the first frame only, read the monitor size via
    `ctx.input(|i| i.viewport().monitor_size)`; when it is `Some`, call `layout::dock_rect` and send
    `egui::ViewportCommand::OuterPosition` and `egui::ViewportCommand::InnerSize` derived from the
    returned rect, then latch a `docked: bool` so it never runs again. When `monitor_size` is `None`,
    leave the builder defaults in place — never guess a monitor size. Per D-15 nothing about position
    or width is persisted; the stripe opens the same way every launch and there is no settings file
    in this phase.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| filesystem → process | The overlay reads local files authored by the same user (`dynamic.json` in a later plan). No file is read from an untrusted source. |
| process → OS windowing | The overlay creates a top-level window. It reads nothing from other processes and writes nothing into them. |

This phase has no network listener, no authentication, no session state, and no third-party input.
RESEARCH § "Security Domain" assessed most ASVS categories as not applicable to a single-user,
offline, read-only desktop overlay; the threats below are the ones that are genuinely real.

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-13-01 | Tampering | New crates.io dependencies (`tray-icon`, `image`, `windows-sys`) | mitigate | Task 1's blocking human legitimacy checkpoint before the first `cargo add`; `Cargo.lock` committed so the resolved versions are pinned. |
| T-13-02 | Tampering | The byte-for-byte filter oracle | mitigate | Every task's acceptance criteria require `cargo test` green and `git status --porcelain tests/fixtures tests/snapshots` empty — a moved fixture is a defect, never a re-baseline (`PITFALLS.md` §4). |
| T-13-03 | Elevation of Privilege | Conduct boundary (D-21/D-22) | mitigate | The overlay reads no game memory, injects no input, and installs no global input hook. Enforced by construction: the only OS APIs this phase touches are window creation and, later, `ShowWindow` on our own HWND. |
| T-13-SC | Tampering | cargo installs | mitigate | Package legitimacy gate (Task 1) — blocking human checkpoint, never auto-approvable, because `slopcheck` did not run (RESEARCH A4). |
| T-13-04 | Spoofing | A rogue `ff.exe` elsewhere on `PATH` | accept | General Windows software-distribution concern, not specific to this overlay; out of scope per RESEARCH § "Security Domain". |
</threat_model>
