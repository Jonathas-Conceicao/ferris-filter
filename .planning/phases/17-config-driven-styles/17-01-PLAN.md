<objective>
Introduce the data model for config-driven styles without changing any consumer yet: a committed
repo-root `styles.json`, an insertion-ordered `StyleSet` type with load-time validation, a
`loader::load_styles` entry point, and the side-by-side equality test that proves the new file
equals the hardcoded `Styles` struct before that struct is deleted (PITFALLS §8c/d). Also make every
test harness copy `styles.json` beside `config.json` now, while doing so is a harmless no-op, so the
later "styles.json is mandatory" commit stays green.

Decision numbering used in all Phase 17 plans (17-CONTEXT.md has no IDs; numbered here in the order
of its "Implementation Decisions" bullets): D-01 styles.json shape (name->style map, same fields,
IndexMap file order, committed at repo root); D-02 initial content is exactly today's 12 styles;
D-03 config.json loses `styles`, generate and the dynamic path both read styles.json, byte-identical
output with no re-baseline; D-04 assert loaded styles.json equals the old values before deleting the
struct, emission order stays fixed in the emitter; D-05 ssf_* configs are not migration targets (clear
error or --styles); D-06 required undeletable styles S..F + unchanged + hidden; D-07 unknown style or
invalid styles.json is a clear load-time error naming the style/field, and a new style needs no code
change; D-08 a style's Show/Hide action overrides the block's; D-09 Hide styles can carry full
visuals; D-10 Claude's discretion (StyleSet name, from_pairs helper, error variants, loader
placement). Orchestrator decisions made on the user's behalf: OD-1 an inline `styles` section in a
config/store file is a load error naming the file; OD-2 optional `--styles <path>` on generate and
apply; OD-3 duplicate style names rejected at load; OD-4 styles.json = exactly today's 12 styles in
today's order and dynamic_base.json loses its styles section too.

This plan implements D-01, D-02, D-04 (equality half), D-06, D-07 (parse/validation half), D-10,
OD-3 and OD-4 (styles.json content).
