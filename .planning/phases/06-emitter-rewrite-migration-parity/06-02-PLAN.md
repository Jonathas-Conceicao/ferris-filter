<task type="auto">
  <name>Task 1: Add the semantic parity test (MIG-02)</name>
  <files>tests/cli_generate.rs</files>
  <action>
Add a helper `generate_early_game() -> String` modeled on `generate_on_seed`, but:
- copies `config.json`, `currency.json`, `prices-fallback.json`, `tiers-fallback.json` from the
  manifest dir into the temp dir (these are the `--early-game` inputs),
- runs `Command::cargo_bin("ferrisfilter").current_dir(&dir).args(["generate", "--early-game",
  "--output", out_path])`,
- returns `normalize(&fs::read_to_string(out_path))`.

Add a block-normalizer + comparator and the test `parity_policy_blocks_match_oracle`:

1. Define `fn split_blocks(filter: &str) -> Vec<Vec<String>>` that splits the filter text into
   blocks. A block starts at a line beginning with `Show` or `Hide` and runs until the next blank
   line. For each block collect ONLY the meaningful lines (the indented condition + action lines,
   trimmed) PLUS a tag for whether it is `Show` or `Hide` (the header keyword). DROP the `# ...`
   comment text on the header (keep only "Show"/"Hide"). Skip pure-comment lines (`#...`) and blank
   lines.

2. Define `fn normalize_block(block: &[String]) -> Vec<String>` that returns the block's lines
   trimmed and SORTED (so within-block condition/action ordering is insensitive), with the
   Show/Hide keyword kept as the first element BEFORE sorting the rest, or simply include "Show"/
   "Hide" as a line and sort everything — pick one and be consistent. The goal: two blocks with the
   same Show/Hide disposition + the same SET of condition/action lines normalize equal.

3. Define `fn policy_blocks(filter: &str) -> std::collections::BTreeSet<Vec<String>>` that:
   - truncates `filter` at the first occurrence of the currency-section marker. Use the line
     `# alwaysShow.currency` OR the `# --- Currency ---` marker as the cut point (everything from
     that line onward is pricer-driven and excluded). Prefer cutting at `# --- Currency ---` since
     that is the first pricer block marker; verify the chosen marker exists in BOTH the oracle and
     the generated output.
   - splits the remaining (policy) text into blocks, normalizes each, and collects them into a
     `BTreeSet` (order-insensitive across blocks).

4. The test:
```rust
#[test]
fn parity_policy_blocks_match_oracle() {
    let generated = generate_early_game();
    let oracle = normalize(&fs::read_to_string(concat!(
        env!("CARGO_MANIFEST_DIR"),
        "/tests/fixtures/parity-baseline-earlygame.filter")).unwrap());
    let gen_set = policy_blocks(&generated);
    let oracle_set = policy_blocks(&oracle);

    // Surface differences explicitly for author review (anything beyond pure reordering).
    let only_in_oracle: Vec<_> = oracle_set.difference(&gen_set).collect();
    let only_in_generated: Vec<_> = gen_set.difference(&oracle_set).collect();
    assert!(only_in_oracle.is_empty() && only_in_generated.is_empty(),
        "policy-block parity mismatch.\n  Only in oracle: {:#?}\n  Only in generated: {:#?}",
        only_in_oracle, only_in_generated);
}
```

The set difference output is the diff report the author reviews at the Task 4 checkpoint. CRLF-
normalize both sides (already handled by `normalize`).

If the test fails, the difference lists tell you exactly which condition/action line differs — fix
the When->filter-line mapping in `src/emitter.rs` (Plan 01) or the rule data in `config.json` until
the policy sets are equal. (Common culprits: `Class ==` vs `Class`, `BaseEnergyShield > 0` vs
`>= 1`, `Rarity` operator/order, a missing/extra condition.)
  </action>
  <verify>
    <automated>cargo test --test cli_generate parity_policy_blocks_match_oracle 2>&1 | grep -q "test result: ok"</automated>
  </verify>
  <done>
`cargo test --test cli_generate parity_policy_blocks_match_oracle` passes. The test references

order- and comment-insensitive. Any non-reorder difference is reported in the assert message.
