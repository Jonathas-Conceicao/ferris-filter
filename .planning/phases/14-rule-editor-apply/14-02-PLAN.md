<objective>
Turn the read-only stripe from Phase 13 into an editable list: rows that expand in place, arrows
that reorder, an Add button, an inline delete confirm, an enable/disable toggle — and the autosave
that makes every one of those durable the moment it happens.

This plan owns the *list*, not the conditions. The expanded body is a single call into a rendering
hook that plan 14-03 fills in; leaving it near-empty here is deliberate, so the accordion, the
identity handling and the save path can be judged on their own.

Purpose: D-01 (accordion, no dynamic resize), D-05 (arrows), D-06/D-07 (append a no-op rule),
D-08 (inline confirm), D-02/D-04 (autosave through the atomic write), D-19 (expansion state keyed
by `RuleId`). Every mutation is a call into plan 14-01's tested functions — this file decides
*when*, never *what*.

Output: `widgets::circular_toggle` and `widgets::arrow_button`; an `app.rs` that owns
`WorkingRules`, `Option<RuleId>`, a delete-confirm target, and a `dirty` flag.
</objective>

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-14-05 | Denial of Service (local) | Autosave frequency — a `DragValue` drag can report `.changed()` every frame, so a careless implementation could write `dynamic.json` dozens of times a second | mitigate | One coalesced write per frame at a single call site over a sub-20KB file on local NTFS (RESEARCH Pattern 5); enforced by the single-`store::save` grep and the no-timer/no-thread grep. |
| T-14-06 | Denial of Service (local) | Losing the last edit when the process exits — the save running after `ViewportCommand::Close` in program order | mitigate | The ordering criterion is asserted by a `grep`-and-compare shell check in Task 3's verify block, plus an at-the-call-site comment naming RESEARCH Risk 4. This is presentation glue, the one category `PITFALLS.md` §8 accepts has no unit-test story, so the ordering check is the guard. |
| T-14-07 | Tampering | Accidental destruction of a rule via a stray click on Delete, with no undo stack this phase | mitigate | D-08's inline confirm: a delete requires two deliberate clicks on the same row. `dynamic_base.json` remains untouched on disk, so `apply --reset` is always available as the floor. |
| T-14-08 | Tampering | The overlay overwriting `dynamic.filter` while the game may be reading it | accept (out of scope here) | This plan writes no filter at all — the `compile_store`/`write_filter` grep criterion proves it. The threat belongs to plan 14-04, where `write_filter`'s existing atomic path mitigates it. |
| T-14-SC | Tampering | npm/pip/cargo installs | mitigate | No package installs in this plan; every crate used is already pinned in `Cargo.toml`. A new dependency would require a blocking human checkpoint before `cargo add`. |
</threat_model>
