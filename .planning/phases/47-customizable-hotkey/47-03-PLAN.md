<objective>
Make the chord a real CONFIG preference end to end: the pending edit in ConfigState, ff-settings.json
as a fourth all-or-none Apply target, registration of the new chord between validation and the
write (old kept until the write succeeds), start-up from the saved value with fallback, and every
place that names the hotkey (tray tooltip / menu line, header close tooltip, second-launch message)
following the live chord. No capture UI here (Plan 04); a chord edit can already be driven by tests
through `ConfigState::set_hotkey`.

Purpose: KEY-02 (pending edit, Apply saves and re-registers without restart, foreground rule kept),
KEY-03 (refusal when another app owns the chord), KEY-04 (fallback at start-up, live chord in the
tray and other mentions).
Output: changes in config_state.rs, apply_all.rs, app.rs, mod.rs, tray.rs, instance.rs; the legacy
constant registration removed from hotkey.rs.
</objective>

Judgement calls (record in SUMMARY and the deferred list):
- Apply ordering is validate -> register -> write (UI-SPEC "Revert, Apply, Quit", judgement 7): a refused registration refuses the whole Apply.
- `ff-settings.json` is not part of the changed-on-disk check (no load baseline); its guard is the bytes read in `prepare` (RESEARCH Pattern 5).
- When CONFIG failed to load there is no ConfigState, so no chord edit can exist (the row is not shown either); nothing special.
- RULES Reload and a root change never re-register (only start-up and Apply register; RESEARCH Pitfall 12).
- `Committed.hotkey_saved` is `Some(chord)` whenever the settings target was committed, whether the writer reported it Written or Unchanged (identical bytes still count as applied, like every other target). `apply_everything` calls `abort_swap(new)` whenever commit returns Ok but `hotkey_saved != Some(new)` (defensive; should not happen), so a registration is never left behind without a saved chord.
- Start-up reads `settings::load(root).0.saved_hotkey()`; an unrelated key warning (e.g. a relative `game_folder`) never discards a valid saved chord. Only an unresolvable FerrisFilter folder yields `saved = None`. The settings warning (including the hotkey's own invalid-value warning from Plan 01) is surfaced by the app's normal settings-load path, and the runtime's in-use warning is joined to it.
- Stale saved chord (no stuck state, author preference): when start-up fell back (the saved `hotkey` was invalid, or valid but in use by another app), the comparison base for "pending" is `None` instead of the live chord, so capturing or resetting to Ctrl+Shift+Z is a real pending edit, Reset stays enabled, and Apply writes `"hotkey": "Ctrl+Shift+Z"` explicitly (registration is a no-op because it is already live). After that Apply the base is the live chord again and the warning stops on the next launch. Helper: `OverlayApp::hotkey_base(&self) -> Option<Chord>` = `None` when `settings.hotkey_invalid` or `settings.saved_hotkey()` is Some and differs from `hotkey.live()`, else `hotkey.live()`. Chosen over removing the key because an explicit value is what UI-SPEC's Settings Contract says a reset writes.
