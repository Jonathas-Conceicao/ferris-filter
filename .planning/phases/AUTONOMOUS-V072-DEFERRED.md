## Open gaps and judgement calls

- Phase 43: the style colour type is `StyleColour([u8; 4])` (no Default or From<[u8;3]>; Eq/Hash derived for Phase 44). Phase 44 must treat a bare 3-token `SetBackgroundColor` as alpha 240, which is not equal to an alpha-255 style.
- Phase 43: the `R G B A` hover tooltip lives in the shared colour slot, so RULES colour cards show it too (only when alpha is below 255).
- Phase 43: quick picks in the colour picker keep the current alpha; the Hex field stays 6-digit RGB only.
- Phase 43: the opaque colour helpers (`colour_slot`, `colour_swatch_rgb`, `StyleView.alpha`) were removed and their tests ported to the alpha path.
- Phase 43: `styles.json` files with 3-value colours stay 3-value on disk until a CONFIG edit is applied (locked decision, no migration flag); `styles-default.json` is 4-value, `tests/fixtures/seed-styles.json` stays 3-value.
- Phase 43: cards and previews paint translucent colours over their dark ground; no checkerboard was added.
- Phase 43: `cargo clippy -D warnings` (134 diagnostics, same count before and after the phase) and `cargo fmt --check` (a few diffs) fail on the floating nightly in code Phase 43 did not introduce; not fixed.
- Phase 43: the Release Review changelog should note that a `styles.json` written by v0.7.2 (4-value colours, saved by any Apply that writes it, including the one that persists ids for an id-less file) cannot be read by older releases; the way back is to delete `styles.json` or use Reset to defaults (WR-01, no code fix by design).
- Phase 43: the UI review (43-UI-REVIEW.md, advisory, 17/24) also suggests a unit test that the `R G B A` swatch tooltip shows only below alpha 255, and the review info items IN-01..IN-05 (dead `ff_colour_card`, always-true `PickerMode::alpha`, "length 5" error text) are left for a later cleanup.
- Phase 47: a saved chord that fails to register for a reason other than "in use" falls back to Ctrl+Shift+Z with the warning `` `hotkey` <chord> could not be registered (<reason>), so Ctrl+Shift+Z is used `` (UI-SPEC only words the in-use case). The tray failure reason for an in-use chord reads `in use by another app`.
- Phase 47: an invalid saved `hotkey` alone gives the status warning `ff-settings.json could not be fully used; `hotkey` is not a usable key combination, so Ctrl+Shift+Z is used.` (the UI-SPEC sentence wrapped in the same form as the other key warnings).
- Phase 47: the keybind border's interior is cleared at extract time (new ff-art `key_white` option) rather than at draw time: egui only alpha-blends, and the irregular white interior reaches into the nine-slice edge pieces, so no draw-time trick removes it without covering the gold corners. Threshold 32 chosen over 96: it also keys the 32-96 grey fringe, which would otherwise stay opaque grey.
- Phase 47: Apply order is validate -> register -> write: a chord another app owns refuses the whole Apply (styles, tiers and filter edits included), nothing is written and every edit stays pending.
- Phase 47: `ff-settings.json` is not part of the changed-on-disk check (it has no load baseline); its guard is the bytes read when the Apply is prepared. RULES Reload and a folder change never re-register the hotkey; only start-up and Apply do.
- Phase 47: after a start-up fallback (saved `hotkey` invalid, or valid but in use), picking or resetting to Ctrl+Shift+Z is still a pending edit and Apply writes `"hotkey": "Ctrl+Shift+Z"`, so the warning stops on the next launch (explicit value rather than removing the key).
- Phase 47: a hotkey-only Apply with no filter loaded reads `Config already up to date. Show / hide is now <chord>.` (the config-only sentence is unchanged).
- Phase 47: README.md and installer/portable-readme.txt still name Ctrl+Shift+Z as the hotkey without saying it can be changed in the Config tab's Overlay section; left for the Release Review wording (agents do not edit them).
- Phase 47: known limitations of the capture: numpad digits register as the main-row digits (egui reports them as the same key), AltGr arrives as Ctrl+Alt, and a few chords (F12 and some Win-reserved ones) may be refused by Windows at Apply, which then shows the in-use refusal.
- Phase 47: the capture cancels on any pointer press outside the keybind button, so a click on the reset button while capturing cancels and then resets (UI-SPEC rule). The capture is drained at the top of the frame, so while capturing no widget sees Ctrl+C / Ctrl+V / Ctrl+X either (egui's Copy / Cut / Paste events are captured as C / V / X).
- Phase 47: the keybind button tints were kept at the UI-SPEC starting values (`pal::GOLD` rest, `#E6C882` lit); the screenshots read close to the game's dark plate with its gold bottom line, so no tuning was done (author's eye check is item above).
- Phase 47: code review WR-05 (author decision needed): Shift is accepted as the one required modifier, so `Shift+Z`, `Shift+1`, `Shift+/`, `Shift+Space` and `Shift+Enter` can be bound, and such a system-wide hotkey swallows that typed character everywhere, PoE2 chat included (the reason the default moved from Shift+Z to Ctrl+Shift+Z). Kept as is per the "at least one modifier" decision. Options: reject Shift-only chords on letters, digits, punctuation, Space and Enter with `Add Ctrl or Alt` (Shift+F-keys and Shift+navigation stay allowed), or keep them with an amber warning on the button.
- Phase 47: code review WR-02 (not fixed, documented in `src/overlay/chord.rs` Known limitations): on non-US layouts a punctuation key is registered as the US `VK_OEM_*` code for its position, which Windows assigns per layout, so the registered key can differ from the one pressed (German QWERTZ: pressing `Ö` shows `Ctrl+;` and registers the `Ü` key). Letters, digits, F-keys and navigation keys are fine. A full fix resolves punctuation through the pressed key's VK (`MapVirtualKeyW(scan, MAPVK_VSC_TO_VK_EX)`) and a layout-aware label, which egui does not expose; alternatively refuse OEM punctuation on non-US layouts.
