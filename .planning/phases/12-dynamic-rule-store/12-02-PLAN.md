<objective>
Make the dynamic flow real and headless: seed `dynamic.json` from `dynamic_base.json`, compile it
to a complete `dynamic.filter` including the economy sections, write that atomically into the game
folder, and expose the whole thing as a CLI subcommand so the feature is usable and scriptable
before any overlay exists (DYN-03, DYN-06, DYN-07, DYN-08).

Most of the compile work is already done: `dynamic_base.json` is a full `Config`, so Phase 11's
`load_inputs` + `compile_as` compiles it with no new emitter path. This plan is the surrounding
lifecycle — where the file comes from, where the output goes, and how it is driven.

**The universal path stays untouched.** `generate`, `sync` and `install` keep their behavior, and
`tests/fixtures/seed-universal.filter` and the snapshot must not move.
</objective>

**`src/compile.rs` — the Phase 11 API this builds on** (plus `compile_as` from plan 12-01):
```rust
pub struct InputPaths { pub config: PathBuf, pub prices: PathBuf, pub tiers: PathBuf,
                        pub prices_fallback: PathBuf, pub tiers_fallback: PathBuf }
impl InputPaths {
    pub fn conventional() -> Self;                       // bare relative names
    pub fn relative_to(root: impl AsRef<Path>) -> Self;
    pub fn with_config(self, path: impl Into<PathBuf>) -> Self;
}
pub enum PriceSourcePolicy { Auto, ForceFallback }
pub enum PriceSource { Live, Fallback(FallbackReason), Absent }
pub struct CompileInputs { pub config: Config, pub priced: PricedData, pub price_source: PriceSource }
pub enum CompileError { Load(..), Rates(..), Generate(..), ForcedFallbackMissing{..} }

pub fn load_inputs(paths: &InputPaths, policy: PriceSourcePolicy) -> Result<CompileInputs, CompileError>;
pub fn compile(inputs: &CompileInputs) -> Result<String, CompileError>;
pub fn compile_as(inputs: &CompileInputs, identity: &FilterIdentity) -> Result<String, CompileError>; // 12-01
```

Compiling the dynamic store is therefore:
`load_inputs(&InputPaths::conventional().with_config("dynamic.json"), Auto)` → `compile_as(&inputs,
&FilterIdentity { output_name: "dynamic.filter", source_name: "dynamic.json" })`. **The economy
sections come along for free** — `load_inputs` runs the same pricer, so DYN-06 needs no extra work.
Verified during discussion: generating from `dynamic_base.json` produced 69 Show / 1 Hide *with*
currency, gem and unique sections.

<task number="1" name="Dynamic store lifecycle: seed, reset, compile, atomic write">
<action>
Create `src/dynamic.rs` (register with `pub mod dynamic;` in `src/lib.rs`) holding the lifecycle,
as plain functions so Phase 14's Apply action can call them directly rather than shelling out:

- **Seeding.** A function that ensures the working copy exists: if `dynamic.json` is absent, copy
  `dynamic_base.json` over it and report that it was created; if present, leave it **completely
  untouched** and report that. Never overwrite an existing working copy — it holds the user's edits.
  Take both paths as parameters (no hardcoded literals outside a small `const`/default helper), so
  the overlay can point at its own root, consistent with Phase 11's CORE-02.
- **Reset.** A separate function that copies the base over the working copy unconditionally. Not
  wired to any UI this phase (D-14) but present and tested, since it is the reason the base file
  exists.
- **Compile.** A function that seeds if needed, loads via
  `InputPaths::conventional().with_config(<dynamic path>)` with `PriceSourcePolicy::Auto`, and
  compiles with `compile_as` and the dynamic `FilterIdentity`
  (`output_name: "dynamic.filter"`, `source_name: "dynamic.json"`). Return the filter text plus
  enough information for a caller to report what happened (at minimum the `PriceSource`, mirroring
  Phase 11's return-don't-print rule — **no `println!`/`eprintln!` in this module**).
- **Atomic write.** A function that writes the text to `<dest>/dynamic.filter` using
  `tempfile::NamedTempFile::new_in(<dest>)` + persist, mirroring `write_prices_atomic`. The temp
  file must live in the destination directory (cross-volume rename otherwise fails — the game
  folder is typically on OneDrive). Error, do not create, when the destination folder is missing —
  matching `cmd_install`'s guard.

Make `install::default_dest` `pub(crate)` and call it rather than re-spelling the path segments.

Unit tests in `src/dynamic.rs`, all building their inputs in a temp dir from committed files:
- seeding creates `dynamic.json` when absent, with content byte-identical to `dynamic_base.json`
- seeding a second time does **not** modify an existing (deliberately altered) `dynamic.json`
- reset **does** overwrite an altered working copy back to the base
- the atomic writer leaves the previous file intact when the destination folder does not exist
- writing twice succeeds and the second content wins
</action>

<task number="3" name="Integration test for the phase's success criteria">
<action>
Add `tests/dynamic_filter.rs` driving the binary end-to-end in a temp dir (assert_cmd, the pattern
`tests/cli_generate.rs` already uses), covering the roadmap's criteria that are not yet proven by
unit tests. Normalize CRLF on both sides of every string comparison — the working tree is CRLF on
Windows while the generator emits LF only.

Cases:
1. **Round-trip + field paths (DYN-01):** a malformed `dynamic.json` (e.g. `"style": 42`) exits
   non-zero with the dotted field path in stderr, exactly as `config.json` does.
2. **Condition independence (DYN-04, criterion 2):** a store containing a single rule that sets only
   `sockets: { min: 3 }` produces a block containing `Sockets >= 3` and **no** `Class`, `Rarity`,
   `BaseArmour`, `BaseEvasion`, `BaseEnergyShield`, `Quality` or `Corrupted` lines.
3. **Ordinal precedence (DYN-02, criterion 3):** swapping two rules in `dynamic.json` swaps the
   order of their blocks in the output.
4. **Economy sections (DYN-06, criterion 4):** `dynamic.filter` generated from
   `tests/fixtures/seed-prices.json` contains the same currency / gem / unique section content that
   `universal.filter` emits from the same prices. Compare the economy portion of both outputs
   directly rather than asserting on a hand-written substring list — that is the assertion the
   criterion actually makes.
5. **No AreaLevel (DYN-05, criterion 5):** the dynamic output contains zero `AreaLevel` lines, while
   a `universal.filter` generated from `config.json` in the same run contains some. Asserting both
   halves is what makes this meaningful.
6. **Persistence (DYN-03, criterion 7):** run once to seed, modify `dynamic.json` (disable a rule),
   run again — the second output reflects the edit, proving the store was read back and not
   re-seeded over.
7. **Disabled rules (12-01 integration):** a rule with `"enabled": false` produces no block, and the
   remaining rules keep their original index labels.

Run everything hermetically: temp dir, binary by absolute path, inputs copied from committed files.
Never `cargo run` from the repo root — it picks up a live `prices.json` (PITFALLS §5, and this
mistake cost time twice during v0.3).
</action>

<threat_model>
Adds a local file-copy (seed/reset) and a local file-write into a user-specified directory, driven
by a new CLI subcommand. No network, no process spawning, no new deserialization format —
`dynamic.json` is parsed by the same `Config` deserializer already used for `config.json`.

- **Write destination (low).** The subcommand writes `dynamic.filter` into a caller-supplied
  folder, defaulting to the resolved game folder. Same exposure as the existing `install --dest`,
  which has shipped since v0.1. The plan requires erroring rather than creating a missing
  destination, matching `cmd_install`'s guard, so a typo'd path fails loudly instead of scattering
  files.
- **Overwriting user state (low, and mitigated).** Seeding must never clobber an existing
  `dynamic.json` — that file holds the user's edits, and this is the only destructive failure mode
  in the plan. Mitigated by an explicit test that seeding twice leaves an altered working copy
  untouched, and by keeping reset a separate, deliberately-called function.
- **Partial writes (low, and mitigated).** The game may read the filter at any moment the player
  hits Refresh; a truncated file fails to load and looks like a tool bug. Mitigated by the atomic
  write-then-rename, with the temp file in the destination directory so a cross-volume rename
  cannot fail mid-operation.

No blocking or high-severity threats. No mitigation tasks beyond those already in the tasks above.
</threat_model>
