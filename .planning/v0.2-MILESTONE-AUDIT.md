# v0.2 Declarative Rule Model — Milestone Audit

**Milestone goal:** Replace the generator's hardcoded gear/flask band logic with a general,
declarative rule schema in `config.json`, so any class + level-range + rarity
(+ defence / quality / sockets / unidentified-tier / base-type) policy is expressible in
config — making the fully-functional in-game filter reproducible from config alone.

**Acceptance bar:** `generate` on the migrated config produces a filter semantically
equivalent to the author's in-game filter (reordering OK).

**Audit date:** 2026-06-12
**Branch:** `milestone/v0.2-declarative-rule-model`
**Test result:** `cargo test` — 154 tests, 0 failures, 4 compiler warnings (test-only dead code)

---

## Requirement Coverage

### RULE-01 — Ordered rules array driving all policy

**Verified.** `config.json` contains a `rules` array of 17 rule objects. `src/emitter.rs`
function `emit_rules` iterates them in authored order, emitting one Show/Hide block per
rule. First-match-wins semantics are preserved by the ordered iteration.

Evidence: `src/emitter.rs` lines 259–363; `config.json` lines 52–214.

### RULE-02 — Named style tier references; Show/Hide follows style action

**Verified.** Each rule's `style` field is resolved at generate-time via `resolve_style`
(emitter.rs lines 59–85), which maps the 11 valid tier names (S/A/B/C/D/E/F/Recycle/
unchanged/hidden/unidentified) to the typed `Styles` struct fields. An unknown name
produces `GenerateError::UnknownStyle` with the offending name and rule index.

Test: `generate_rejects_unknown_style_name` (emitter::tests) passes.

### RULE-03 — No class-specific emitter code paths remain

**Verified.** A grep for `emit_gear_bands`, `emit_flask_charm_bands`, `emit_recycle` across
`src/` returns zero matches. The emitter contains exactly three top-level section functions:
`emit_header`, `emit_rules` (all policy), `emit_currency_sections`, `emit_unique_sections`
(pricer-driven; unchanged from v0.1). No gear/flask/charm/recycle/jewellery class branches.

Test: `pricer_section_present_and_unchanged` asserts the policy section contains no
`Class == ` (the pricer's exact-match form), confirming all policy is emitted via
`emit_rules` with bare `Class`.

### COND-01 — Class list (any-of)

**Verified.** `When.class: Option<Vec<String>>` in config.rs. Emitted as bare `Class "A" "B"`
(space-separated quoted values, no `==`). Used in 15 of 17 rules in config.json.

### COND-02 — Rarity comparator (==, >=, <=)

**Verified.** `RarityComparator` with `RarityOp` (Eq/Gte/Lte) in config.rs lines 157–238,
with full custom Deserialize/Serialize. Compact string format `">=Magic"`, `"<=Rare"`,
`"Rare"` (bare = Eq). Emitted as `Rarity >= Magic`, `Rarity <= Rare`, `Rarity == Rare`.

Tests: `rarity_comparator_bare_is_eq`, `rarity_comparator_gte_magic`,
`rarity_comparator_lte_rare`, `rarity_comparator_eq_prefix_unique`,
`rarity_comparator_rejects_unknown_rarity`, `rarity_comparator_rejects_bad_op`,
`rarity_comparator_rejects_multibyte_without_panic`, `rarity_comparator_round_trip`,
`rarity_comparator_eq_serializes_bare` — all pass.

### COND-03 — Area level min/max (open-ended)

**Verified.** `AreaLevelRange { min: Option<u32>, max: Option<u32> }`. Either side optional.
Emits `AreaLevel >= N` and/or `AreaLevel <= N`. Used with min-only, max-only, and both bounds
across the 17 config rules.

Tests: `area_level_range_both_bounds`, `area_level_range_min_only`,
`area_level_range_max_only` — all pass.

### COND-04 — Numeric attributes (BaseArmour, BaseEvasion, BaseEnergyShield, Quality, Sockets)

**Verified.** `NumericCondition { eq, min, max }` with `emit_numeric` helper (emitter.rs
lines 234–249). Defence attribute `min: 1` emits `> 0` (matching the oracle filter). All
five attributes are modeled as named fields on `When`.

Tests: `numeric_condition_eq_zero`, `numeric_condition_min_one`,
`numeric_condition_rejects_unknown_key`, `when_all_condition_fields_populate` — all pass.

### COND-05 — BaseType list

**Verified.** `When.base_type: Option<Vec<String>>`. Emitted as `BaseType == "A" "B"` (with
`==` — exact-match semantics). Used in `unidentified high-tier: jewellery` — wait, checking:
the unidentified rules use `class` + `unidentifiedTier`, not `baseType`. The `baseType` field
is modeled, tested with `rule_full_round_trip`, and confirmed parseable from config. The
representative rules JSON in tests exercises it. Not used in the current 17-rule policy
because policy does not need explicit BaseType filtering (currency/unique BaseType filtering
is pricer-driven, outside `rules`). Correctness confirmed by model test and emitter path.

### COND-06 — UnidentifiedItemTier threshold

**Verified.** `UnidentifiedTier { min: u32 }` in config.rs. Emitted as
`UnidentifiedItemTier >= N`. Used in two rules: "unidentified high-tier: weapons + armour"
(min: 4) and "unidentified high-tier: jewellery" (min: 4).

Test: `unidentified_tier_min` passes.

### CAP-01 — Build weapons Magic+Rare up to configurable area-level cap

**Verified.** Rule "bands 26+: build weapons Magic+Rare (capped)" in config.json with
`areaLevel: { max: 75 }` and `rarity: ">=Magic"`. The `cap_is_rule_driven` integration test
mutates the 75 to 60, regenerates, and asserts `AreaLevel <= 60` present and
`AreaLevel <= 75` absent — passes.

### CAP-02 — Build-armour upper area-level cap

**Verified.** Rules "band 26-45: build armour (ES / hybrid)" and "bands 46+: build armour
(pure ES)" both carry `areaLevel.max: 75`. The `cap_is_rule_driven` test covers both (the
mutation replaces all `"max": 75` occurrences) — passes.

### CAP-03 — Flask/charm mid-band Magic+Rare + Hide fallback bounded by rarity

**Verified.** Rule "bands 26-65: magic flasks/charms" with `rarity: ">=Magic"` and
`areaLevel: { max: 65 }`. Rule "flasks/charms fallback" with `style: "hidden"` and
`rarity: "<=Magic"`. Both present in config.json.

### CAP-04 — Charms independently targeted (Normal charms at area level >= 78)

**Verified.** Rule "bands 78+: normal charms" targeting only `class: ["Charms"]` with
`areaLevel: { min: 78 }` and `rarity: "==Normal"`. Confirmed in config.json.

### CAP-05 — Jewellery (Rings/Amulets/Belts <= Rare) hidden via config

**Verified.** Rule "jewellery fallback: hide low-rarity Rings/Amulets/Belts" with
`style: "hidden"` and `rarity: "<=Rare"`. Policy parity confirmed by `parity_ingame` test.

### CAP-06 — High-tier unidentified items (UnidentifiedItemTier >= N) highlighted

**Verified.** Two rules using style `unidentified`: one for all gear/weapon classes
(min: 4), one for jewellery classes (min: 4). The `unidentified` style exists in both
`config.json` (styles section) and `src/models/config.rs` (`Styles.unidentified` field).
`resolve_style` maps the name at generate-time.

### MIG-01 — config.json migrated; serde models validate with field-path errors

**Verified.** `config.json` is fully migrated to the rules schema. The `loader.rs` uses
`serde_path_to_error` for field-path-aware errors on bad input. The `config_parses_real_file`
test passes. `malformed_config_json_reports_field_path_and_expected_type` integration test
passes (cli_errors suite).

### MIG-02 — generate produces filter semantically equivalent to in-game filter

**Verified.** `parity_ingame` integration test passes with zero non-reorder policy-block
differences between `generate --early-game` and `tests/fixtures/parity-ingame.filter`. Only
the pricer/currency section differs (Vaal Infuser/Tablets removed from price data — data
drift, not policy). Author confirmed in-game filter works.

### MIG-03 — Parity oracle committed; artifact-guard/snapshot fixture re-baselined

**Verified.** Both fixtures exist:
- `tests/fixtures/parity-ingame.filter` — in-game oracle (Phase 7 parity gate)
- `tests/fixtures/seed-universal.filter` — snapshot oracle (artifact_guard gate)

Tests `artifact_guard` and `generate_snapshot` pass against these fixtures.

### MIG-04 — Price-driven currency/unique sections unchanged

**Verified.** `pricer_section_present_and_unchanged` integration test asserts:
- `# --- Currency ---` marker present
- Currency tier blocks S through F present
- `Class == "Stackable Currency"` (with `==`) present in pricer blocks
- Policy section contains no `Class == ` (confirming pricer and policy are distinct code paths)

### DOC-01 — CLAUDE.md realigned; "unverified" caveats cleared

**Verified.** A search for "unverified" and "verify before use" in CLAUDE.md returns zero
matches. The `UnidentifiedItemTier` entry now reads "confirmed PoE2 (author-tested, v0.2)".

in-game (author-tested, v0.2)" callout block. A full "Declarative rule model" section
documents the `rules` array, `when` vocabulary, and all named styles including `unidentified`.

## Deferred Items (Not Gaps)

The following items were explicitly out of scope for v0.2 and remain on the post-v0.2 backlog:

- **BaseType-matched tablet category** — `prices-fallback.json` / `tiers-fallback.json` still
  contain a Tablets entry that is now an invalid Class in the game. The current workaround
  removes Tablet/Vaal Infuser rows from the fetched price data at sync time (fix in commit
  c0c1a54). A proper BaseType-scoped rule for tablets is deferred (documented in
  `.planning/phases/07-new-capabilities-docs/07-CONTEXT.md` Deferred Ideas).

- **Generate QoL** (`--dry-run`, `--diff`, `-v`, stale-prices warning) — GENX-01..04,
  explicitly deferred in REQUIREMENTS.md Future Requirements.

- **Sync extensions** (multi-profile, alternate price source) — SYNX-01..02, deferred.
